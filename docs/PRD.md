# PRD — Landing Page Builder (v1)

> Status: Draft v1 · Owner: Design Platform · Last updated: 2026-05-17
> Repo: `Ohouse-product-design/LandingPage-Builder`
> 네이밍 규칙은 [CONVENTIONS.md](./CONVENTIONS.md)를 단일 소스로 한다.

## 1. 배경

오늘의집은 신사업(이사, 인테리어, 전문가 매칭, 커머스 버티컬 등)을 빠르게 늘려가는 중이며 이에 따라 **신규 랜딩페이지 수요가 폭증**하고 있다. 그러나 모든 버티컬이 본질적으로 같은 구조(배너 → 핵심 가치 → 절차 → 후기 → CTA)를 반복함에도, 현재는 매번 디자이너가 처음부터 화면을 조립한다.

이로 인해 두 가지 문제가 누적된다.

- **공급 병목.** 디자이너가 단일 공급원이 된다. 비디자이너(엔지니어, PO, PM, BD)는 기획 의도와 콘텐츠가 명확해도 자력으로 랜딩페이지를 출시할 수 없다.
- **룩앤필 일관성 붕괴.** 비디자이너가 자체적으로 만들면(HTML 스텁, 마케팅 툴, 임의 Figma 익스포트 등) 오늘의집 디자인 시스템(ODS 토큰, 타이포 리듬, 모션)을 거의 따르지 않는다.

랜딩페이지 빌더는 **디자이너가 승인한 프리셋**을 비디자이너가 조립할 수 있도록 가이드하면서, 동시에 **카탈로그(어떤 프리셋이 존재하는지)에 대한 권한은 디자이너에게 유지**시키는 도구다.

## 2. 목표

1. **비디자이너 unblock.** 엔지니어/PO/PM/BD가 디자이너의 손을 빌리지 않고 신사업 랜딩페이지를 런칭 가능한 수준까지 조립한다.
2. **오늘의집 룩앤필 보존.** 모든 페이지는 디자이너가 작성한 프리셋과 ODS 토큰화된 컴포넌트의 조합으로만 구성된다.
3. **자연어 의도를 구조로 변환.** 기획 의도가 담긴 프롬프트("서비스 주요 항목을 안내하는 섹션을 추가해줘")가 적절한 섹션 프리셋으로 해석되고, 페이지에 자동 배치된다.
4. **디자이너가 카탈로그를 통제.** Storybook이 "어떤 프리셋/컴포넌트가 존재하는가"의 단일 소스다. 디자이너는 Storybook에서 카탈로그를 확장하고, 빌더는 그 변경을 자동으로 반영한다.

## 3. 비범위 (Non-Goals · v1)

- **자유 레이아웃 / 픽셀 조정.** 드래그 리사이즈, 요소별 타이포 오버라이드 없음. 전부 프리셋 + 슬롯이다.
- **프롬프트로 새로운 비주얼 생성.** LLM은 기존 프리셋 중 선택만 한다. 신규 컴포넌트 생성은 v1 범위 밖.
- **멀티 테넌트 / 외부 퍼블리싱.** 출력 타깃은 오늘의집 내부 서피스 한정 (초기: Apps Script 퍼블리셔, 이후: CDN/CMS).
- **CMS급 콘텐츠 워크플로.** 다단계 승인, 로컬라이제이션 워크플로, 예약 배포 없음. 검수 핸드오프(Jira/Slack)가 유일한 워크플로 프리미티브.
- **모바일 어드민.** 빌더 UI는 데스크톱 전용. 프리뷰만 반응형.

## 4. 타깃 유저 & 페르소나

### P1 — 비디자이너 컴포저 (메인)
신사업 버티컬을 런칭하는 엔지니어 / PO / PM / BD. 비즈니스 의도와 카피는 알지만 디자인 툴 숙련도는 낮고, 페이지를 이번 주 안에 띄워야 한다.

- 원하는 것: "필요한 걸 말로 설명하면 부끄럽지 않은 페이지를 만들어주는 도구."
- 현재 불편함: 디자이너 일정에 막힘. 임시 도구를 쓰면 브랜드 일관성이 무너짐.
- 성공 기준: 풀 디자인 사이클이 아닌, 디자이너의 1회 리뷰만으로 브랜드 안전한 페이지를 출시.

### P2 — 카탈로그 오너 디자이너 (메인)
오늘의집 전반의 랜딩페이지 패턴을 책임지는 디자이너.

- 원하는 것: "Storybook에서 시스템을 한 번 작성하면, 비디자이너가 그것만으로 조립한다."
- 현재 불편함: 모든 버티컬의 랜딩페이지에 끌려 들어감. 일회성 페이지들이 ODS에서 이탈.
- 성공 기준: 디자이너가 손대는 페이지 비율 감소. 리뷰 큐는 "조립 작업"이 아닌 "카탈로그 갭/엣지 케이스"에 한정됨.

### P3 — 리뷰 디자이너 (서브)
P1이 조립한 페이지의 검수 요청을 받는 디자이너.

- 원하는 것: 처음부터 Figma 핸드오프가 아닌, 명확한 diff와 원본 기획 의도.
- 성공 기준: 카탈로그 내 페이지의 검수 회신 1영업일 이내.

## 5. 유저 스토리

### P1 — 비디자이너 컴포저
- PM으로서, 빈 페이지에서 "서비스 주요 항목을 안내하는 섹션을 추가해줘"라고 입력하면, 카드 그리드 구조의 프리셋(`section.card-grid`)이 적절한 슬롯과 함께 삽입된다.
- 엔지니어로서, 타이틀과 슬롯 콘텐츠를 입력할 때 글자수·줄수 제약이 인라인으로 강제되어 디자인 판단이 필요 없다.
- BD로서, 빌더 안에서 모바일/태블릿/데스크톱 프리뷰를 전환할 수 있다.
- PO로서, 한 번의 클릭으로 디자이너 검수 요청을 보내고, 그 요청이 현재 드래프트 링크와 함께 Jira/Slack에 도착한다.

### P2 — 카탈로그 오너 디자이너
- 카탈로그 오너로서, Storybook에 새 섹션 프리셋(타이틀 디폴트 + 슬롯 + uiSpec)을 추가하면, 빌더 코드 변경 없이 "+ 섹션 추가" 메뉴에 등장한다.
- 카탈로그 오너로서, 새 컴포넌트 프리셋(슬롯에 들어가는 단위)을 Storybook에 추가하면, 호환되는 슬롯에서 선택 가능해진다.
- 카탈로그 오너로서, 프리셋을 `pinned`로 표시(예: header/footer)하면 비디자이너가 삭제·재정렬할 수 없다.

### P3 — 리뷰 디자이너
- 리뷰어로서, 검수 요청을 열면 (a) 페이지 프리뷰, (b) 사용된 프리셋 목록, (c) 각 섹션을 만들어낸 원본 프롬프트가 보인다.

## 6. 핵심 플로우

### 6.1 프롬프트 → 프리셋 배치 (핵심)

```
[P1 프롬프트 입력]
     │
     ▼
[Intent 분절 (LLM)] ──► 단일 의도 vs 다중 의도 판단
     │                  다중일 경우 N개의 IntentSignal 로 분리
     │
     ▼ (의도마다 반복)
[Intent 추출 (LLM)] ──► { intent: "introduce_features",
                          cardinality: "multi",
                          tone: "informational" }
     │
     ▼
[프리셋 매처] ──► 후보: [ section.card-grid,
                         section.card-list,
                         section.table ]
                  현재 페이지 컨텍스트와 프롬프트 시그널로 스코어링
     │
     ▼
[최상위 후보 자동 배치] ──► 커서 위치 다음(또는 직전 의도 다음)에 삽입
                            기본 타이틀 + 빈 슬롯
     │
     ▼
[P1 슬롯 콘텐츠 입력] ──► uiSpec이 글자수/줄수 제약 강제
     │
     ▼
[프리뷰 실시간 업데이트]
```

폴백: 신뢰도가 임계값 미만이면 자동 배치 대신 상위 2~3개 후보를 선택 UI로 표시한다.

다중 의도 예시: "배너 추가하고 그 아래에 서비스 항목 안내 섹션 만들어줘" → LLM이 2개 의도(`promote_hero`, `introduce_features`)로 분절 → 각각 매칭하여 순서대로 배치.

### 6.2 매뉴얼 섹션 추가 (이스케이프 해치)

"+ 섹션" 드롭다운은 카탈로그의 모든 프리셋을 노출한다(오늘 기준 `section-add-menu.ts` 가 단일 소스). 프롬프트 플로우와 무관하게 항상 사용 가능하다.

### 6.3 카탈로그 확장 (요청 기반)

카탈로그 확장은 **검수 플로우를 트리거로** 동작한다. P1이 조립 중 적절한 프리셋이 없거나, 리뷰어가 검수 중 카탈로그 갭을 발견하면 검수 요청에 카탈로그 확장 항목을 포함시킨다.

```
[P1 또는 리뷰어가 카탈로그 갭 인지]
   │
   ▼
검수 요청 모달에서 "카탈로그 확장 요청" 체크
   ├─ 무엇이 필요한지 자연어로 기술
   └─ 참고 사례 (현재 페이지, 유사 디자인) 첨부
   │
   ▼
[Jira 티켓 + Slack 메시지 발송]
   ├─ 라벨: catalog-extension
   └─ 라우팅: 디자인 플랫폼 팀
   │
   ▼
[디자이너 + 개발자 후속 작업]
   ├─ 디자이너: 새 프리셋의 시각/구조 정의 → Storybook 스토리 작성
   ├─ 개발자: (필요 시) 새 컴포넌트 구현
   └─ 둘 다: 프리셋 컨트랙트 충족 + intent 태그 자동 생성 검증
   │
   ▼
[CI가 레지스트리 재생성 → 빌더에 자동 연동]
   │
   ▼
"+ 섹션" 메뉴 + LLM 매처가 모두 새 프리셋 인지
```

스토리 작성 시점에 intent 태그는 **자동 생성**된다 (스토리 메타데이터 + LLM 분석 기반). 디자이너는 필요 시에만 오버라이드한다. 자동 태깅 메커니즘은 SPEC §3.4 참고.

### 6.4 검수 핸드오프

P1이 "검수 요청" 클릭 → 모달에서 리뷰어 + 메모 + (선택) 카탈로그 확장 요청 입력 → 빌더가 Jira 티켓 + Slack 메시지를 생성. 프리뷰 URL과 프롬프트 히스토리가 포함된다. 카탈로그 확장 요청이 포함되면 §6.3 의 후속 플로우로 분기된다.

### 6.5 코드 Export (개발자 초안)

검수 통과 후 또는 그 이전에도, 조립한 페이지를 **개발자가 1차 코드 초안으로 바로 사용할 수 있는 정적 번들**로 내보낼 수 있다. 빌더의 라이브 프리뷰가 그대로 옮겨질 수 있도록 HTML/CSS/에셋 링크가 반응형 스펙과 함께 묶인다.

```
[P1 또는 개발자가 "코드 Export" 클릭]
   │
   ▼
[Export 모달]
   ├─ 포맷: 정적 HTML+CSS (디폴트) / 컴포넌트 스니펫 (React JSX)
   ├─ 토큰 인라인 여부: CSS 변수로 :root 에 인라인 (디폴트) / Tailwind 클래스 유지
   └─ 에셋 처리: 절대 URL 유지 (디폴트) / zip 동봉
   │
   ▼
[빌더가 LandingPageDoc → 번들 변환]
   ├─ index.html        시맨틱 마크업 + ARIA 속성
   ├─ styles.css        ODS 토큰 변수 + 반응형 규칙 (375 / 768 / 1280)
   ├─ assets.json       사용된 이미지·Lottie URL 매니페스트
   ├─ links.json        섹션·CTA 의 anchor href 매니페스트
   └─ README.md         반응형 스펙·바인딩 토큰·교체 포인트 안내
   │
   ▼
[zip 다운로드 또는 GitHub Gist 링크]
```

- 출력은 빌더 프리뷰와 **시각적으로 동일**해야 한다. 토큰·간격·타이포가 1:1.
- HTML 마크업은 시맨틱 태그(`<header>`, `<section>`, `<article>`, `<footer>`)와 ARIA 라벨을 포함해 개발자가 접근성 추가 작업을 최소화한다.
- CSS 는 mobile-first 작성. 375 / 768 / 1280 의 3 브레이크포인트가 명시적으로 선언된다 (단순 미디어 쿼리, 빌더 프레임워크 의존성 없음).
- 토큰은 `:root` 의 CSS 변수로 인라인되어, 개발자가 자신의 ODS 토큰 시스템과 비교·동기화하기 쉽다.
- Export 번들은 "초안"이며, 라이브 페이지 권위 소스가 아니다. 운영 페이지의 최종 마크업/스타일은 개발자가 빌드 파이프라인에 통합한 결과가 권위 있는 소스가 된다.

## 7. 기능 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1 | 빌더는 Storybook에서 생성된 단일 레지스트리로부터 섹션 프리셋 카탈로그를 로드한다. | P0 |
| FR-2 | 비디자이너는 (a) 프롬프트 → 프리셋, (b) 매뉴얼 "+ 섹션" 피커, (c) 섹션별 타이틀 + 슬롯 편집만으로 페이지를 조립할 수 있다. | P0 |
| FR-3 | 프롬프트 입력은 자유 형식의 한국어/영어 텍스트를 수용한다. 시스템은 LLM 으로 의도를 추출하고 매칭되는 프리셋을 제안한다. | P0 |
| FR-3-1 | 프롬프트에 다중 의도가 포함되면 LLM 이 N 개 의도로 분절하고, 각 의도에 대해 매칭·배치를 독립적으로 실행한다. | P0 |
| FR-4 | 매처의 신뢰도가 임계값 이상일 때 자동 삽입, 그 외엔 상위 후보 중 사용자가 선택. | P0 |
| FR-5 | 모든 프리셋은 기본 타이틀과 이름 있는 슬롯을 선언한다. 타이틀과 슬롯 콘텐츠는 `uiSpec`으로 실시간 검증된다. | P0 |
| FR-6 | `pinned` 프리셋(header, banner, sticky-bar, footer 등)은 비디자이너가 재정렬·삭제할 수 없다. **단, 카피(타이틀·서브타이틀·CTA 라벨 등) 편집은 허용된다.** | P0 |
| FR-7 | 프리뷰는 375 / 768 / 1280 px에서 반응형으로 렌더된다. | P0 |
| FR-8 | 새 섹션/컴포넌트 프리셋은 프리셋 컨트랙트를 만족하는 Storybook 스토리 추가만으로 등록되며, CI가 레지스트리를 재생성해 빌더에 자동 연동된다. 빌더 코드 변경 불요. | P0 |
| FR-8-1 | 프리셋의 `intents` 태그는 빌드 타임에 스토리 메타데이터(타이틀, 슬롯 구성, 컴포넌트 종류)와 LLM 분석으로 **자동 생성**된다. 디자이너는 필요 시에만 수동 오버라이드한다. | P0 |
| FR-9 | "검수 요청" 액션은 Jira 티켓을 생성하고 Slack에 메시지를 발송한다. 프리뷰 링크와 각 섹션의 원본 프롬프트 히스토리를 포함한다. | P1 |
| FR-9-1 | 검수 요청 모달은 **카탈로그 확장 요청** 옵션을 포함한다. 체크 시 Jira 티켓에 `catalog-extension` 라벨이 부여되고, 디자인 플랫폼 팀으로 라우팅된다. 후속 작업(디자이너·개발자의 Storybook PR)이 머지되면 FR-8 경로로 자동 반영된다. | P1 |
| FR-10 | 페이지 문서(`LandingPageDoc`)는 영속 저장되고 재오픈 가능하다. v1은 오토 세이브 허용. | P1 |
| FR-11 | 섹션 추가/삭제/재정렬/타이틀 편집에 대한 Undo/Redo. | P1 |
| FR-12 | 감사 로그는 누가 무엇을 변경했는지, 그리고 (프롬프트로 추가된 섹션의 경우) 원본 프롬프트를 기록한다. | P2 |
| FR-13 | 빌더는 조립된 페이지를 정적 HTML + CSS + 에셋·링크 매니페스트 + 반응형 스펙으로 export 한다. 개발자가 자신의 코드베이스에 1차 초안으로 그대로 사용할 수 있어야 한다. | P1 |
| FR-13-1 | Export 출력은 mobile-first CSS 와 375 / 768 / 1280 px 의 명시적 미디어 쿼리를 포함한다. ODS 토큰은 `:root` CSS 변수로 인라인된다. | P1 |
| FR-13-2 | Export 출력은 React JSX 스니펫 포맷도 옵션으로 지원한다 (각 섹션별 컴포넌트로 분리, 슬롯은 props 로). | P2 |

## 8. 제약 & 의존성

- **디자인 시스템.** 모든 비주얼 프리미티브는 ODS 토큰(`src/schema/ods-tokens.ts`)과 Tailwind 설정에서 와야 한다. 빌더는 임의 색상/타이포를 도입하지 않는다.
- **Storybook 단일 소스.** 프리셋 레지스트리는 Storybook 스토리에서 생성되며, 스토리 작성 컨벤션이 컨트랙트다 (SPEC §3 참고).
- **LLM 공급자.** Intent 추출은 호스팅 LLM을 호출한다. LLM 장애 시 매처는 매뉴얼 피커로 그레이스풀하게 강등된다.
- **퍼블리싱.** 초기 출력 타깃은 Apps Script 웹앱(`apps-script/`). CDN/CMS는 후속 마일스톤.
- **네이밍 컨벤션.** 모든 프리셋·슬롯 ID는 [CONVENTIONS.md](./CONVENTIONS.md)의 구조적 명명 규칙을 따른다. 비즈니스 의미가 담긴 ID(예: `usp`, `review`)는 금지.

## 9. 리스크 & 완화책

| 리스크 | 영향 | 완화책 |
|---|---|---|
| LLM이 의도를 오분류해 잘못된 프리셋을 삽입. | 사용자 좌절. "동작하지 않는 매직" 인식. | 신뢰도 게이트 자동 삽입 + 폴백 선택 UI + 1클릭 undo + 프롬프트/선택 로깅으로 오프라인 튜닝. |
| 디자이너와 비디자이너의 "충분히 좋다" 기준이 분기. | 리뷰 길어지고 빌더 신뢰도 하락. | `uiSpec` 엄격 강제. 리뷰어가 돌릴 동일 체크를 빌더에 노출. P2와 주간 카탈로그 리뷰. |
| 카탈로그가 큐레이션 속도보다 빠르게 성장해 프롬프트 매칭 노이즈 증가. | 매처 정확도 하락. UI 산만. | 프리셋마다 intent 태그 강제. 매처는 태그 + 임베딩 사용. 분기별 카탈로그 정리는 P2 담당. |
| Storybook이 빌더 런타임 의존성이 됨. | 빌드 속도 저하. 커플링. | Storybook 빌드 타임에 정적 아티팩트로 레지스트리 생성. 빌더는 아티팩트만 소비. |

## 10. 마일스톤

### M1 — 카탈로그 기반 매뉴얼 조립 (기반)
빌더가 Storybook 기반 레지스트리에서 프리셋 카탈로그를 로드. 비디자이너가 "+ 섹션" 피커로 페이지 조립 가능. 프리뷰와 uiSpec 검증이 엔드 투 엔드로 동작. *현재 대부분 구현됨.*

### M2 — 프롬프트 → 프리셋 (핵심 unlock)
LLM intent 추출기 + 프리셋 매처. 신뢰도 게이트 자동 삽입 + 폴백 선택 UI. 섹션별 프롬프트 히스토리 영속화.

### M3 — 디자이너 확장 루프 클로즈
Storybook 스토리 작성 컨벤션 문서화. CI가 레지스트리 생성. 새 프리셋이 PR → 빌더 라이브까지 빌더 코드 변경 없이 도달.

### M4 — 검수 핸드오프 프로덕션화
Jira + Slack 통합이 mock을 대체. 검수 요청에 프롬프트 히스토리와 프리셋 목록이 포함.

### M5 — 퍼블리싱
Apps Script mock을 CDN/CMS 퍼블리시로 교체. `LandingPageDoc`의 SSR 렌더.

## 11. 결정사항 & 오픈 이슈

### 결정사항 (v1)

- **`pinned` 프리셋의 카피 편집은 허용.** 비디자이너는 header/banner/sticky-bar/footer 의 타이틀·서브타이틀·CTA 라벨을 편집할 수 있다. 구조(재정렬·삭제·슬롯 변경)는 여전히 잠긴다. (FR-6)
- **다중 섹션 프롬프트 지원.** LLM 이 프롬프트를 N 개 의도로 분절하고 각각을 독립 매칭·배치한다. (FR-3-1, SPEC §4.6)
- **카탈로그 태깅은 자동.** 빌드 타임에 스토리 메타데이터와 LLM 분석으로 `intents` 가 생성된다. 디자이너의 수동 태깅은 오버라이드 용도로만 사용. (FR-8-1, SPEC §3.4)
- **카탈로그 확장은 검수 트리거 기반.** 비디자이너 또는 리뷰어가 검수 요청에 "카탈로그 확장" 항목을 포함시키면 Jira/Slack 으로 발송되고, 후속 디자이너·개발자 작업이 머지되면 빌더에 자동 연동된다. (FR-9-1, §6.3)

### 오픈 이슈

- 권한: 누가 퍼블리시, 누가 조립, 누가 카탈로그 확장 PR 머지? SSO 그룹 게이팅 예정. 디테일은 M4 에서 플랫폼 팀과 협의.
